# CareWeave AI

**A journey-state intelligence and action layer for pharmacy benefits.**

CareWeave holds each member's cross-system pharmacy journey as a single
time-ordered object, continuously scores it for impending friction, grounds every
explanation in retrieved policy, and selects from a closed set of twelve
permitted actions — with a human in the loop wherever confidence or impact
demands it.

> All data is synthetic and generated by this repository. No real people, no real
> medications, no real prices, no real plan documents. This is a research
> prototype, not a clinical or production system. See
> [docs/limitations.md](docs/limitations.md).

---

## Why this exists

Two industry conversations about AI in healthcare converge on the same diagnosis:
the answers a member needs usually exist somewhere, but not assembled, not
explained, and not at the moment the decision is being made. Service is reactive,
so the member has to hit a wall first. Advocates start every call reconstructing
context by hand.

Five whys on a single support call — *a member calls, confused about a medication
they cannot get* — lands on a structural cause:

> **No component owns the member's cross-system state over time, or decides at
> each moment whether that state is about to become a problem.**

That missing component is the product. Everything else is a feature of it.

## What it is not

| It is | It is not |
|---|---|
| A journey-state engine with an action policy | A chatbot with a database behind it |
| Grounded explanation with plan-scoped citations | A RAG demo |
| A calibrated risk score gating a controlled intervention | A dashboard of invented numbers |
| A closed action space the language model narrates | An agent that decides what to do to a patient |
| A synthetic-data research prototype | Anything clinically validated |

## Measured results

Every number below is produced by `make all` and written to `data/artifacts/`.
None is hand-entered.

### Friction risk model

Predicts whether a member will contact support, escalate, or abandon a fill
within 14 days. Trained on 27,237 point-in-time observations, split
chronologically with a 14-day purge between folds.

| Model | Test PR-AUC | Read |
|---|---|---|
| Majority baseline | 0.147 | the base rate |
| Logistic regression | 0.329 | a linear model already beats it |
| **LightGBM (selected)** | **0.398** | interactions matter |
| LightGBM, calibrated | 0.379 | isotonic calibration costs a little discrimination and buys usable probabilities |

Held-out test: ROC-AUC 0.788, calibration error 0.048, **2.58× lift** over the
base rate.

Because operations capacity is finite, queue precision is the decision-relevant
view:

| Queue | Precision | Lift |
|---|---|---|
| Top 5% | 53.6% | 3.65× |
| Top 10% | 45.5% | 3.09× |
| Top 20% | 34.0% | 2.31× |

The risk bands the governance gate keys on separate cleanly on held-out data:

| Band | Share of cases | Observed friction rate |
|---|---|---|
| Low | 64.4% | 6.0% |
| Medium | 31.5% | 26.8% |
| High | 4.1% | 58.1% |

Top features by permutation importance: unresolved prior contacts, days since
last rejection, days since last contact, portal views, prior-authorization
rejections, refill runway. All map to a problem named in the source material.

### Policy retrieval

40 hand-written, hand-labelled questions phrased the way members and advocates
actually phrase them, over a 61-chunk corpus.

| Metric | Score |
|---|---|
| Correct document in top 1 | 85% |
| Correct document in top 3 | 95% |
| Correct *section* in top 3 | 90% |
| Mean reciprocal rank | 0.907 |

### Reading the member's words

2,639 messages and call transcripts, scored against the generator's own
pre-text ground truth.

| Metric | Score |
|---|---|
| Intent identified | 99.0% |
| Clinical questions caught | 100% (209 of 209), 100% precision |

**The 99% is optimistically biased and should not be quoted as general
extraction accuracy.** The text comes from a finite template set and the rules
were tuned after seeing failures on that same text. It shows the pipeline and
the harness work — not that extraction is solved. Clinical recall is the metric
that matters, because a miss routes a safety question to an automated answer.

## The three things that make it defensible

**1. A closed action space.** The model never chooses what to do. Twelve
enum-typed actions, each with an evidence contract stating which records and
document types must exist before it is permitted. The generative layer receives
an already-selected action and writes prose for it. A test asserts every action
has a contract and that the policy can only return enum members.

**2. The Friction Ledger.** Every terminal path writes one immutable audit
record — including the paths where the system deliberately did nothing. Silence
is a governed decision. Inputs, model versions, evidence ids, reason codes, gate
verdict, human override and outcome are all queryable, so "why did this member
get this message on this day" is answered without re-running anything.

**3. Grounding is verified, not requested.** Every numeral in a generated
response must appear in the grounded facts, the retrieved evidence, or the
deterministic draft. Anything else is flagged and the response falls back to the
draft, which is grounded by construction. A separate test asserts that every
number in the static templates actually appears in the policy corpus.

## Architecture

```
Journey events ──► Journey Store (point-in-time, as_of enforced in ONE place)
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
  Signal extraction  Feature builder   Member 360
  (LLM + rules)      (leakage-safe)         │
        │               │                  │
        └──────► Friction Risk Model ◄──────┘
                        │
                 Context Engine — what / why / evidence / next / now
                        │
                 Policy Retrieval (plan-scoped, cited)
                        │
                 Next-Best-Action Policy  ← closed set of 12
                        │
                 Governance Gate  ──► suppress · hold · escalate
                        │
       Member reply  ·  Advocate copilot  ·  Human review (graph suspends)
                        │
                 Friction Ledger (every path, including no-action)
```

### Why LangGraph earns its place

Not because agents are fashionable. Four properties of this problem need an
orchestrator:

1. **Workflows suspend for days.** A prior authorization opens Tuesday and
   resolves the following Monday. Checkpointing keyed on `case_id` means resuming
   is a lookup, not a replay, and the process may exit in between.
2. **Human review is a graph primitive.** `interrupt()` stops mid-execution,
   persists state, and resumes from that exact node when a reviewer responds.
3. **Routing is conditional on model output.** Risk band, evidence sufficiency
   and gate verdict each fork the path, declared as edges rather than buried in
   nested conditionals.
4. **Execution is observable.** The UI streams node-by-node so a reviewer watches
   the graph run.

Nodes are deliberately thin — read state, call one plain-Python component, write
state. All decision logic is importable and testable without a graph runtime.

## Quick start

```bash
make install
make all        # generate data, train, evaluate, run scenarios, run tests
make api        # then open http://localhost:8000
```

Runs entirely offline. No API key. The default LLM profile is a deterministic
stub, so anyone who clones the repository gets identical output. Setting
`CW_LLM_PROVIDER=anthropic` swaps in real model calls behind the same interface;
every evaluation runs against both, so "what did the language model add?" has a
number rather than an assertion.

```bash
docker compose up   # same thing, containerised
```

## Demo scenarios

`make scenarios` runs six cases, each **found by searching the population for
structural conditions** rather than hand-picked:

| Scenario | What it demonstrates |
|---|---|
| Cost surprise | Multi-source cost explanation, plan-scoped citation |
| Authorization pending, supply running out | Proactive detection before contact |
| Repeat contact | Escalation beats a fourth explanation; human modifies the recommendation |
| Claim rejection | Reconciling claim, formulary and authorization records |
| Clinical question | The engine refuses and routes to a pharmacist |
| Proactive intervention | Blocked paperwork surfaced before the member calls |

The refusal path is included on purpose. A system that only demonstrates its
successes has not been demonstrated.

## Tests

```bash
make test    # 36 invariant tests
```

These are not coverage tests. Each asserts a property that would otherwise break
*silently*: no feature reads the future, a prior authorization decided after
`as_of` reads as pending, the gate has no path to upgrade a verdict to ALLOW, a
clinical question cannot be automated at any confidence, retrieval cannot cite
another plan's benefit summary, and the ledger records deliberate no-action.
